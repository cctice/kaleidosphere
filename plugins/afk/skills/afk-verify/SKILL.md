# afk-verify — 自动验证与反馈闭环

AFK 的精髓所在：**AI 自己跑验证、自己修问题、自己复跑，直到收敛或如实报告卡点。** 让人可以 Away From Keyboard。

## 职责

1. **验证运行器**：找出项目真实的验证入口并执行，整理成验证记录。
2. **反馈闭环**：把失败项逐条消化成"结论 + 修复 + 回流路径"，未消化的如实挂起。

## 固定流程（SOP）

### 第一步：探测验证入口

按顺序探测，找到第一个可用的：

1. `package.json` 的 `scripts.test` / `scripts.check`（npm / pnpm / yarn 按锁文件判断）
2. `Makefile` 的 test/check 目标
3. 仓库内 `test*/`、`*.test.*`、`*_test.*` 文件（可直跑 node:test / pytest / go test）
4. 都没有 → 明确声明"无可运行验证环境"，列出能做的替代检查（语法检查、结构检查、构建），**不得编造通过结果**

### 第二步：执行并记录

- 运行验证命令，记录：命令、退出码、耗时、失败清单（测试名 + 首行错误）。
- 验证记录落盘为产物文件（建议放 `.afk/artifacts/verification-<时间戳>.md`），包含：环境、命令、结果、失败分类。

### 第三步：修复循环（核心）

对每个失败项，最多 **3 轮**：

```
定位（读失败输出+相关源码，说出触发条件）
→ 最小修复（只改导致失败的原因，不顺手重构）
→ 重跑该失败项所在的最小测试集
→ 通过则跑全量；仍失败则进入下一轮
```

- 3 轮未收敛：停止修，写明"卡点"（现象、已排除的假设、建议人工介入点），不得无限重试烧 token。
- 修复改变了外部行为 → 必须同步更新对应测试，禁止为绿改断言。

### 第四步：反馈回流

验证记录里每个条目必须落在一个状态里：

| 状态 | 含义 |
|---|---|
| resolved | 已修复且复跑通过，注明修复 commit/文件 |
| wont_fix | 有理由不修（如过时测试），写明理由 |
| escalated | 卡点，写明现象与建议介入点 |

回流规则：resolved 且属于实现问题的 → 回 `implementation` 阶段补登记；需求歧义导致的 → 回 `requirement` 阶段澄清；都不是 → 留在 `delivery` 摘要的遗留事项。

### 第五步：登记产物

```bash
node <afk>/skills/afk-flow/scripts/afk.js complete --root <项目根> \
  --output-path <验证记录路径> --purpose "自动化验证记录与修复闭环结论"
```

## 铁律

- 没跑过 = 没通过。任何"应该没问题"都不算数。
- 不删失败测试、不改断言凑绿、不跳过（skip）自己修不了的用例。
- 只读默认：修代码属于验证闭环的一部分，但改动必须最小化且在记录中逐条列出。

## 输出要求

产物路径、产物作用、resolved/wont_fix/escalated 统计、剩余风险、`produced_by: afk-verify`。
