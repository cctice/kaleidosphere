# afk-dev — 开发执行与自评审

AFK 的双手：先按最小步幅把代码写对，再自己当评审员把 diff 挑一遍毛病。写完就跑 `afk-verify`，两技能接力。

## 一、开发执行（最小步幅 TDD）

### 固定流程

1. **读上下文**：当前任务、相关源码、已有测试。明确对外行为与最小验证入口。
2. **先写会失败的测试**：对行为变更先写一个表达意图的失败测试，跑一次确认失败原因正确（证明测试有效）。
3. **最小实现**：只写让该测试通过的最少代码。
4. **重跑**：测试通过后视需要重构，重构后再跑。
5. **循环**：按任务粒度重复 2–4，直到任务完成。

### 判断标准（防机械 TDD）

- 复制、重命名、纯注释/文案/配置修改：用对应的结构检查（编译、lint、schema 校验）验证，**不补实现镜像测试**。
- 没有可运行测试环境：说明限制，用可行的替代验证（构建、类型检查、定向运行），不能编造通过结果。
- 每步都保持可运行：不留"下一轮再修"的破损状态。

## 二、自代码评审（写完必走）

对自己刚产生的 diff 做一轮默认必走的审查，标准与审查他人一致：

### 固定流程

1. **圈范围**：当前分支 / 工作树 / 本轮改动 diff。
2. **读调用点**：改动牵涉的调用方与测试，确认没有破坏隐含契约。
3. **逐条报告**：只报告能解释**触发条件**和**影响**的问题，每条标注优先级（P0 阻断 / P1 应修 / P2 建议）、文件、行号。
4. **明示未覆盖项**：没有发现问题时，明确写出检查范围与未覆盖的盲区（如并发、大数据量、平台差异）。

### 审查清单

- [ ] 边界与空值：空集合、null/undefined、越界、负数
- [ ] 错误路径：失败分支是否吞错、资源是否释放（fd/锁/子进程）
- [ ] 隐含契约：函数签名、返回结构、并发调用假设
- [ ] 安全基线：注入、路径拼接、反序列化、密钥硬编码
- [ ] 测试缺口：新行为是否有测试钉住

### 行为约束

- 审查默认只读；只有用户已授权修复时才动代码（修完回 `afk-verify` 复验）。
- 发现 P0 → 立即修，修完复跑测试再继续报告其余项。

## 三、登记产物

开发记录（改动范围、验证入口、实际验证结果/限制）落盘后登记：

```bash
node <afk>/skills/afk-flow/scripts/afk.js complete --root <项目根> \
  --output-path <开发记录或评审记录路径> --purpose "<build：实现与测试 / self_review：自评审结论>"
```

## 输出要求

产物路径、产物作用、实际验证结果或限制说明、剩余风险、`produced_by: afk-dev`。
